# NEEV Assumptions Register — Phase 1, Phase 2 & Phase 3

| Assumption ID | Topic | Current Understanding / Assumption | Confidence Status | Implementation Effect | Resolution Required By |
|---|---|---|---|---|---|
| **ASM-001** | APAAR Identifier Format | Official APAAR is a 12-digit numeric identifier. Cleaned strings are checked with regex `^\d{12}$`. | Partially Confirmed | Used in rule `APA-002`. Malformed values are flagged without corrupting database integrity. | Phase 3/4 (Live API agreement) |
| **ASM-002** | External Government Integrations | Live APAAR, DigiLocker, NAD, and AISHE APIs are not authorized in Phase 1 & Phase 2. | Confirmed | Implemented behind simulated adapters; all statuses explicitly marked `SIMULATED` or `UNAVAILABLE`. Never presented as official live government verification. | Phase 4 (Production authorization) |
| **ASM-003** | Supernumerary & NRI Seat Rules | Treatment of supernumerary, PMSSS, and NRI seats varies by state and programme type. | Unconfirmed Policy | Evaluates raw approved intake against active enrolments, with rule `INT-002` identifying discrepancies as explainable findings rather than automatic accusations. | Phase 3 (Regulatory policy formalization) |
| **ASM-004** | Academic Year Boundaries | Standard academic cycle spans July 1 to June 30 of the following year. | Confirmed | Modelled explicitly in `academic_years` table rather than arbitrary date arithmetic. | Established in Phase 1 baseline |
| **ASM-005** | Historical Records Preservation | A student may have historical completed or transferred records that do not conflict with subsequent active enrolments. | Confirmed | Database avoids simplistic blanket uniqueness on student identity; reconciliations count only records where `enrolment_status == 'ACTIVE'`. | Established in Phase 1 baseline |
| **ASM-006** | Sole Database Engine Requirement | PostgreSQL is the sole supported database across development, testing, staging, and production. SQLite is strictly disallowed as an application option, test database, fallback, or alternative runtime configuration. | Confirmed | Application rejects non-PostgreSQL URLs at startup, tests run exclusively against dedicated PostgreSQL databases (`neev_test`), and duplicate migration trees are consolidated into `backend/migrations`. | Established in Phase 1 Remediation |
| **ASM-007** | Password Recovery Email Delivery | Live government email gateways (NIC / Gov.in SMTP) are not provisioned in local development. | Confirmed | Implemented behind development email adapter and audit logs; reset tokens are hashed with SHA-256 and expire in 15 minutes. | Phase 4 (Production infrastructure deployment) |
| **ASM-008** | Controlled Account Provisioning | Public self-registration is strictly disallowed for this regulatory system. | Confirmed | Accounts are provisioned exclusively by authorized national administrators (`PLATFORM_ADMIN`, `AICTE_ADMIN`) with explicit roles and institution scopes. | Established in Phase 1 Remediation |
| **ASM-009** | APAAR Comparison Key Stability | Keyed HMAC-SHA256 fingerprint uses a dedicated server-side secret (`APAAR_FINGERPRINT_KEY`) separate from authentication secret. | Confirmed | Prevents rainbow table lookup while enabling exact-match cross-institution conflict detection. Key rotation requires an offline re-indexing script. | Phase 3 |
| **ASM-010** | Evidence Local Filesystem Storage | Cloud object storage (S3/MinIO/GCS) is not provisioned for local development. Evidence is stored in private backend directory `backend/storage/evidence/`. | Confirmed | Files are stored with UUID-hashed names and non-executable extensions outside web roots. Storage interface is kept modular for cloud driver swap in Phase 4. | Phase 4 |
| **ASM-011** | Local Malware Scanning Status | Dedicated antivirus daemon (e.g. ClamAV) is not running locally on developer workstations. | Confirmed | Uploaded documents are tagged with scanning status `CLEARED_LOCAL` and logged as un-quarantined. In production, an asynchronous scanning pipeline will be mandated before clearing documents. | Phase 4 |
| **ASM-012** | Mandatory Rationale Threshold | Rule `WF-002` requires a minimum of 10 characters for terminal finding transitions (`RESOLVED`, `DISMISSED`, `ESCALATED`) and record corrections (`HIS-001`). | Confirmed | Enforced at the service layer with informative HTTP 422 responses. Prevents empty or meaningless single-word justifications. | Established in Phase 2 baseline |
| **ASM-013** | Legitimate Transfer Transitions | An enrolment record at Institution A marked `TRANSFERRED` or `WITHDRAWN` with an admission/transfer date preceding or matching Institution B is recognized as `DUP-004` (Legitimate transfer). | Confirmed | Does not trigger an adverse `DUP-002` fraud finding. Verified with synthetic demonstration cases. | Established in Phase 2 baseline |
| **ASM-014** | In-App Notification Transport | External communication gateways (SMS, WhatsApp, SMTP) are not provisioned. | Confirmed | Notifications are delivered strictly in-app via database-backed table `notifications` with read/unread tracking and unread counter badges. | Established in Phase 2 baseline |
| **ASM-015** | Illustrative Risk Weights & Versioning | Weights (Capacity: 25, Conflict: 25, Quality: 15, Roster: 15, Source Gap: 10, Repeated: 10) are prototype defaults codified under version `1.0.0`. | Working Prototype Default | Implemented in `RiskEngineService`; rules are deterministic and versioned without AI/ML. Historical calculations store inputs snapshot and version for permanent auditability. | AICTE Executive Committee formal adoption |
| **ASM-016** | Risk Band Prioritization Interpretation | Risk bands (Routine: 0–19, Watch: 20–39, Review Recommended: 40–59, Priority Review: 60–100) are workflow prioritization indicators, not proof of fraud or automatic penalties. | Confirmed | Stated explicitly across UI headers, factor breakdown profiles, and API responses. The system never displays or calculates fraud probabilities. | Phase 3 baseline |
| **ASM-017** | Audit Case State Machine Enforcements | Cases follow strict server-enforced state machine: `OPEN` → `ASSIGNED` → `UNDER_REVIEW` → `CLARIFICATION_REQUESTED` → `RESPONSE_RECEIVED` → `UNDER_REVIEW` → `RESOLVED` / `ESCALATED` / `CLOSED_NO_ACTION`. | Confirmed | Direct illegal jumps are rejected with HTTP 422. Terminal states mandate review rationale. Reopening is blocked unless explicitly authorized. | Phase 3 baseline |
| **ASM-018** | Confidentiality of Internal Reviewer Notes | Reviewer notes flagged `is_internal = True` are restricted exclusively to regulatory officers (`REGULATOR_OFFICER`, `SYSTEM_ADMIN`). | Confirmed | Filtered at database query and service layer before serialization. Notes are never exposed in institutional endpoints, notifications, or report exports. | Phase 3 baseline |
| **ASM-019** | Formula Injection Neutralization | CSV export cells beginning with `=`, `+`, `-`, `@`, `\t`, or `\r` are neutralized by prepending a single quote `'`. | Confirmed | Enforced in `ReportingService` across all 10 standard report types. Protects regulatory officers and institutional staff when opening exports in Excel/Sheets. | Phase 3 baseline |
| **ASM-020** | Report Artifact Retention & Expiry | Generated report CSV files are stored locally in `backend/storage/reports/` with UUID filenames. | Confirmed | Persisted for audit and compliance inspection. Automated TTL-based deletion policy is scheduled for Phase 4 cloud storage integration. | Phase 4 (Cloud Object Lifecycle) |
| **ASM-021** | Cross-Tenant Report Isolation | Non-national users are restricted to generating and downloading reports strictly for their permitted institution ID. | Confirmed | Backend rejects unauthorized downloads with HTTP 403. National aggregate reports are forbidden for institutional scope. | Phase 3 baseline |
| **ASM-022** | Limited-Purpose Verification References | Verification references demonstrate proof of enrolment without disclosing raw APAAR identifiers or full student records. Bearer tokens (`neev_vrf_...`) are hashed with SHA-256 at rest, and resolver enforces synthetic disclaimer: "Synthetic demonstration — not an official APAAR verification." | Confirmed | Implemented in `VerificationService` and Alembic migration `db148c417e94`. Claims are minimized to allowlisted fields only. | Phase 4 Release Candidate |
| **ASM-023** | Concurrency Control for Verification Limits | Row locking (`with_for_update(of=VerificationReference)`) is used on PostgreSQL to guarantee atomicity of verification use limits under concurrent access. | Confirmed | Tested with concurrent requests; prevents race conditions where simultaneous checks bypass `max_uses`. | Phase 4 Release Candidate |
| **ASM-024** | External Integrations Simulation | All 5 external integration adapters (`APAAR_DIGILOCKER`, `AISHE_PORTAL`, `NAD_PORTAL`, `STATE_TECH_BOARD`, `AICTE_APPROVAL_PORTAL`) are strictly simulated prototypes; no live government production or sandbox APIs are fabricated or claimed. | Confirmed | Exposes status, latency, supported claims, and known limitations in `integration_status_logs`. Live integration requires formal government inter-ministerial data-sharing agreements. | Production deployment / Government sign-off |
| **ASM-025** | Sensitive Data Redaction in Logging | 12-digit APAAR numbers are redacted as `••••-••••-XXXX` and passwords/tokens as `[REDACTED_SECRET]` in application logs. | Confirmed | Implemented via `SensitiveDataRedactingFilter` in `app/core/logging_config.py`. Prevents PII and secrets leakage in server logs. | Phase 4 Release Candidate |
| **ASM-026** | PostgreSQL Sole Database and Disaster Recovery | PostgreSQL is the sole application database. Database backups use `pg_dump -Fc` and disaster recovery is verified via automated restore drill (`scripts/backup_restore_drill.py`). | Confirmed | Zero SQLite anywhere in the repository. Full restore drill verified with 100% table row parity across all 39 relational tables. | Phase 4 Release Candidate |
| **ASM-027** | Release Candidate Classification | Platform is labeled `Release candidate — not approved for real student data` pending formal external security audit, government legal clearances, and official integration authorization. | Confirmed | Prominently stated across documentation, dashboard notices, and verification resolver results. | Release Candidate milestone |
